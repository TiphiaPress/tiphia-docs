# 分支与版本管理

TiphiaPress 使用轻量的 `dev -> main` 分支模型。它适合当前这种多仓库、快速迭代、但仍需要稳定发布的项目节奏。

## 分支职责

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `dev` | 日常开发分支 | 新功能、重构、文档补充、插件集成都先进入这里。 |
| `main` | 稳定发布分支 | 只接收从 `dev` 合并而来的稳定版本。 |
| `feature/*` | 可选功能分支 | 较大的功能从 `dev` 拉出，完成后回合 `dev`。 |
| `fix/*` | 可选修复分支 | 集中修 bug；紧急生产修复可以从 `main` 拉出，再回合 `dev`。 |
| `release/*` | 可选发布准备分支 | 发布候选期使用，用于只接受修复和文档补充。 |

## 开发规则

- 小改动可以直接提交到 `dev`。
- 大改动建议使用 `feature/<short-name>`。
- 不要在 `main` 上做日常开发。
- 发布前必须确认 `dev` 已完成构建、测试和文档更新。
- 如果 `main` 有热修复，修复后必须同步回 `dev`。

## 版本号建议

后端、前端和主题可以独立发布，但对外推荐用同一套发布说明描述兼容关系。

建议格式：

```text
v0.4.0
v0.4.1
v0.5.0-rc.1
```

版本含义：

- `MAJOR`：破坏性 API、配置或插件接口变更。
- `MINOR`：新增功能，保持兼容。
- `PATCH`：bug 修复、文档、样式、构建修复。
- `rc`：候选版本，用于发布前验证。

## 合并到 main 前检查

后端：

```bash
cargo fmt --check
cargo check --workspace
cargo test --workspace
```

前端：

```bash
yarn build
```

文档：

```bash
node --check site.js
```

部署：

- Docker 镜像能启动。
- 配置文件方式能启动。
- Nginx 静态前端刷新 `/admin`、`/posts/*` 不 404。
- CORS 只允许真实前端域名。
- Redis 配置存在时限流能连接成功。
