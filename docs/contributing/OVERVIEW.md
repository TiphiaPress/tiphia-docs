# 协作说明总览

TiphiaPress 目前按职责拆分为多个仓库：后端核心、前端骨架、默认主题、文档站，以及若干独立插件仓库。协作规范的目标不是增加流程负担，而是让这些仓库在长期迭代时保持可追踪、可发布、可回滚。

## 基本原则

- 开发中的改动先进入 `dev` 分支。
- 稳定版本从 `dev` 合并到 `main`。
- 不直接把未验证的新功能、大重构或插件集成提交到 `main`。
- 跨仓库改动要在提交说明或 PR 描述中写清楚影响范围。
- 任何公开 API、配置项、Options key、Hook、主题配置字段变更，都要同步更新文档。

## 适用仓库

| 仓库 | 内容 | 协作重点 |
| --- | --- | --- |
| `tiphia` | Rust 后端核心、后端插件、迁移工具、Docker | 数据库迁移、API 兼容、Hook 契约、部署配置。 |
| `tiphia-frontend` | 前端骨架、后台管理、默认集成插件、主题加载机制 | 骨架与主题解耦、插件 Hook、i18n、静态部署。 |
| `tiphia-default-themes` | 默认主题源码 | 主题配置、前台展示、主题 HookSlot、响应式样式。 |
| `tiphia-docs` | 中文文档站 | API、部署、开发范式、插件主题开发说明。 |
| 独立插件仓库 | 插件后端与前端配置面板 | 插件默认禁用、配置完整性、日志和失败策略。 |

## 日常工作流

1. 从 `dev` 拉取最新代码。
2. 创建功能分支或直接在 `dev` 上做小改。
3. 完成代码、测试和文档。
4. 提交时使用约定格式。
5. 较大的改动通过 PR 合并到 `dev`。
6. 发布前从 `dev` 做构建、测试、部署 smoke test。
7. 稳定后合并到 `main` 并打 tag。

## 跨仓库改动说明

如果一个功能同时影响多个仓库，建议按以下顺序处理：

1. 后端契约：API、Hook、Options key、数据库结构。
2. 前端骨架：数据获取、类型、插件注册、主题注册。
3. 主题或插件：具体 UI 和交互。
4. 文档：部署、开发、插件/主题使用说明。

提交或 PR 描述中应写清楚：

- 影响了哪些仓库。
- 是否需要数据库迁移。
- 是否需要重新构建前端。
- 是否需要修改生产配置。
- 是否向后兼容旧配置和旧插件。
